# Flowline

Локальное однопользовательское приложение: Git-контекст, редактор DAG и реальные
блоки AI и CMD. Go backend, системная SQLite и интерфейс без npm-зависимостей.
Backend находится в `backend/`, рабочий интерфейс — в `frontend/`.

## Запуск

Требуются Go 1.27+, Git, C-компилятор и библиотека/заголовки SQLite (CGO).
Для GitHub нужен `gh`, для подписочных
исполнителей — соответствующий CLI с выполненным входом.

Из корня проекта:

```sh
make run
```

Или:

```sh
cd backend
go run ./cmd/service
```

Откройте **http://127.0.0.1:4173**. Сервер принимает только loopback IP.
Всё состояние хранится в **`~/.flowline/`** и доступно для всех добавленных проектов:

```text
~/.flowline/
  settings.json   настройки сервера и исполнителей
  flowline.db     репозитории, пайплайны и история запусков
  worktrees/     изолированные рабочие деревья запусков
  server.lock    блокировка общего каталога данных
```

SQLite также может создавать служебные `flowline.db-wal` и `flowline.db-shm`.
Путь к данным не зависит от каталога запуска или расположения исходников Flowline.
Каталог и база создаются при запуске; `settings.json` можно скопировать из примера
или создать первым сохранением настроек исполнителей.
Для другого порта: `go run ./cmd/service --listen 127.0.0.1:4174` из `backend`.
Параметры `--data` и `--frontend` меняют расположение данных и интерфейса.

Сборка: `make build`. Готовый файл запускается из `backend` командой
`../bin/flowline`; из другого каталога передайте абсолютный `--frontend`.

## Настройки

Готовый пример — [`examples/settings.json`](examples/settings.json). Из корня проекта:

```sh
mkdir -p -m 700 ~/.flowline
cp -n examples/settings.json ~/.flowline/settings.json
chmod 600 ~/.flowline/settings.json
```

`cp -n` сохраняет уже существующий файл. Пример содержит адрес сервера и профили
Codex CLI, Claude Code и DeepSeek API. Секретов в нём нет: `apiKeyEnv` задаёт только
имя переменной окружения с ключом, подписочные CLI используют свою авторизацию.

| Поле | Назначение |
| --- | --- |
| `listen` | Loopback IP и порт; по умолчанию `127.0.0.1:4173`. |
| `dataDir` | Общий каталог SQLite и рабочих деревьев. По умолчанию `~/.flowline`, независимо от каталога запуска. |
| `frontendDir` | Каталог интерфейса. По умолчанию `../frontend` относительно каталога запуска. |
| `executors` | Профили исполнителей. Отсутствующее поле включает стандартные профили; `[]` явно отключает все профили. |

Пути из файла могут содержать `~/`; относительные пути считаются от каталога
`settings.json`. Пути в флагах `--data` и `--frontend` считаются от текущего каталога.
Явно переданные `--listen`, `--data` и `--frontend` имеют приоритет над файлом.
Другой файл можно выбрать через `--settings /absolute/path/settings.json`.
Неизвестные поля, некорректный JSON и внешний адрес сервера приводят к явной ошибке
запуска. Явно указанный через `--settings` файл должен существовать.

Редактирование файла вручную применяется после перезапуска Flowline. Изменения
профилей в окне «Исполнители» применяются сразу и атомарно сохраняются в этот же
`settings.json`, сохраняя параметры сервера. Сам запуск файл не переписывает.

Если стандартный `~/.flowline/settings.json` ещё отсутствует, Flowline читает
прежний `<каталог данных>/executors.json` (по умолчанию `~/.flowline/executors.json`);
при отсутствии обоих файлов использует
стандартные профили. Первое сохранение через «Исполнители» создаёт новый
`settings.json`. Если он уже существует, старый файл не используется.
Старая `.flowline/` внутри проекта автоматически не подхватывается. Если в ней есть
данные, до их переноса можно продолжить работу через `--data /absolute/path/.flowline`.
Существующий `dataDir` или явно переданный `--data` по-прежнему выбирает указанный каталог;
для общего хранилища удалите это переопределение или задайте `"dataDir": "~/.flowline"`.

## Первый сценарий

1. Нажмите «Добавить репозиторий» и укажите абсолютный путь к существующему Git-репозиторию.
2. Выберите ветку и PR. GitHub-авторизация используется из `gh auth login`.
   Можно запустить локальную ветку без PR. Ошибки доступа и несовпадение SHA отображаются явно.
3. Для AI настройте профиль в «Исполнители». CMD работает и с пустым списком профилей.
   Создайте пайплайн, при необходимости из шаблона
   «Разработка → Ревью → Тестирование → Публикация».
4. Добавьте блоки AI/CMD, связи, JSON-вход и выходы. Для AI задайте промпт,
   для CMD — Bash-скрипт. Сохраните и запустите.
5. В снимке запуска выберите блок: доступны фактический JSON-вход, подставленный промпт
   или буквальный скрипт, результаты, stdout/stderr CMD, логи, код завершения, diff
   и путь рабочего дерева.

Начальная база не содержит демонстрационных репозиториев, PR или запусков.
Шаблон создаёт только редактируемую конфигурацию.

## Исполнители

- **Codex CLI:** сохранённая подписочная авторизация; foreground `exec`,
  sandbox `workspace-write`, без разрешения эскалаций, структурированный результат.
- **Claude Code:** сохранённая авторизация; `acceptEdits`, без интерактивных запросов
  разрешений. Требуется версия с `--permission-prompts none` (2.1.259+).
  Команды, которым нужны дополнительные разрешения, дают явную ошибку.
- **Совместимый API:** настраиваемые HTTPS base URL и модель; DeepSeek входит в
  начальные профили. В UI задаётся **имя** переменной окружения, например
  `DEEPSEEK_API_KEY`. Значение установите в окружении процесса до запуска backend.
  После изменения окружения перезапустите приложение.

Наличие CLI в PATH не означает действительную авторизацию; её результат виден
при реальном вызове. Профили хранятся в `~/.flowline/settings.json` без ключей.
Замена профиля не меняет уже запущенные и исторические конфигурации.

API-исполнитель умеет читать/записывать обычные файлы своего worktree, перечислять
файлы и запускать проверки. На macOS проверки запускаются через системный sandbox
без сети и с записью только в worktree/выделенный временный каталог. API-команды
проверок на Linux пока не поддержаны; доступны файловые инструменты и CLI-адаптеры.
Ссылки, служебные файлы Git, распространённые файлы секретов и специальные файлы
для API-файловых инструментов закрыты. Неудачная проверка должна быть успешно
повторена, иначе блок завершится ошибкой независимо от текста ответа модели.

## Граф и данные

Граф ацикличный. Блок запускается после успеха всех входящих зависимостей;
одновременно выполняются до четырёх блоков в одном запуске. Отказ зависимости
помечает downstream-блоки как пропущенные, независимые ветки могут продолжаться.

У блоков и выходов стабильные ID. Примеры подстановок:

```text
{{context}}                 полный Git-контекст
{{branch}}                  выбранная ветка
{{commit}}                  исходный SHA
{{pull_request}}            PR или отсутствие PR
{{changes}}                 однозначный выход прямого предшественника
{{node_id.changes}}         квалифицированное имя
{{my_input}}                явно связанный именованный вход
```

Неоднозначные/отсутствующие ссылки блокируют запуск. Переименование выхода обновляет
связанные ссылки в промптах AI и строковых значениях JSON, в том числе квалифицирует
возникшие коллизии. Для нескольких выходов AI ожидается JSON-объект с объявленными
именами. Координаты и масштаб сохраняются.

SQLite хранит репозитории, пайплайны и историю. Каждый запуск фиксирует граф,
Git SHA/ветку/PR и определения исполнителей. Три SQL-миграции встроены в бинарник;
редактирование пайплайна или профиля не переписывает историю.

## Блоки AI и CMD

Палитра содержит два типа исполнения. Названия «Разработка», «Ревью» и остальные
этапы остаются названиями AI-блоков в шаблонах. Старые типы `develop`, `review`,
`test`, `publish`, `prompt` и пустой тип совместимы с AI. Неизвестный тип — ошибка.
Старый блок без поля `inputJson` сохраняет прежнее исполнение промпта; редактор
не меняет его при открытии. Редактирование JSON включает новый формат входа.
Исторические снимки не преобразуются, миграция БД для этих полей не нужна.

У новых блоков `inputJson` — редактируемый текст JSON-объекта, по умолчанию `{}`.
Пустой текст, массив, `null`, некорректный JSON и отсутствующие/неоднозначные ссылки
отклоняются до выполнения. Внутри строк разрешены ссылки, например:

```json
{"task":"Проверь изменения", "previous":"{{node_id.stdout}}", "branch":"{{branch}}"}
```

Подстановка структурная: кавычки и переводы строк остаются данными и не ломают JSON.
Ключи объекта не шаблонизируются; значения результатов не подставляются повторно.
Фактическая оболочка имеет поля:

```json
{
  "context": {"repository": {"id":"repo", "name":"project", "path":"/path/to/repo", "remote":""}, "branch":"main", "sha":"commit-sha", "pr":null},
  "predecessors": {"node_id": {"stdout":"previous text", "stderr":"", "exitCode":"0"}},
  "inputs": {"branch":"main", "node_id.stdout":"previous text"},
  "data": {"task":"Проверь изменения", "previous":"previous text", "branch":"main"}
}
```

`inputs` содержит все доступные встроенные ссылки, однозначные выходы и явные
псевдонимы (пример сокращён). `predecessors` включает результаты прямых
предшественников по ID, поэтому одинаковые имена выходов разных веток не теряются.
`data` содержит пользовательский объект после подстановки. Эта оболочка сохраняется
в деталях запуска с редактированием распознаваемых секретов.

**AI** требует доступный настроенный профиль и непустой промпт. Flowline автоматически
добавляет JSON-вход к инструкциям для модели. Именованный протокол выходов сохранён.

**CMD** требует непустой `command`, отдельный от промпта. Flowline запускает
`/bin/bash --noprofile --norc -e -o pipefail -c <command>` в отдельном worktree блока.
Доступны несколько команд, переменные и конвейеры. Полная JSON-оболочка поступает
на stdin; небольшой рабочий пример без дополнительных программ:

```bash
input=$(cat)
printf '%s\n' "$input"
printf 'finished\n' >&2
```

Скрипт — буквальный код: ни `{{reference}}`, ни данные предшественников в него
не подставляются. Данные из stdin не выполняются как команды. Для чтения отдельных
полей используйте JSON-парсер, уже доступный в вашем проекте. CMD использует
окружение и права процесса backend; worktree изолирует изменения Git, но не является
системным sandbox. Исполняйте доверенный код и не применяйте `eval` к входным данным.

По умолчанию CMD создаёт `stdout`, `stderr`, `exitCode`. Потоки сохраняются отдельно,
включая пустые строки. Поле `source` выхода выбирает поток; его можно переименовать,
сохранив ID и источник, например `{"id":"out1","name":"report","source":"stdout"}`.
При отсутствии `source` допускается стандартное имя потока. У выходов AI `source`
не используется. В карте выходов код завершения — строка, в деталях блока — число.
Ненулевой код, ошибка конвейера или превышение лимита вывода завершают блок ошибкой;
stdout/stderr и код сохраняются, зависимые блоки пропускаются. Отмена использует
тот же guardian, который завершает процессы блока и их потомков.
Лимиты: 4 MiB на поток, 64 KiB на незавершённую строку, 256 KiB на журнал блока.

## Git и публикация

Каждый блок работает в отдельном detached worktree. Пользовательский исходный
checkout не переключается, не сбрасывается и не отправляется в stash. Исходные
незакоммиченные изменения не входят в запуск: его база — выбранный commit SHA.

После успешного блока изменения фиксируются локальным служебным коммитом с
отключёнными hooks/signing. Следующий блок получает этот commit; join объединяет
коммиты предшественников. Конфликт слияния — ошибка, артефакты остаются для просмотра.
Рабочие деревья сохраняются в `~/.flowline/worktrees/`. Автоматической очистки пока нет.

**Публикация в этой версии** готовит локальные описание PR, сводку проверок и
релизные заметки. Результаты и diff сохраняются в истории. Push, изменение/создание
PR, merge и выпуск релиза не реализованы и автоматически не выполняются Flowline.
Пользовательские CLI-промпты исполняются с правами и ограничениями выбранного CLI.

GitHub — первый адаптер за общим интерфейсом. Перед запуском PR перечитывается;
сверяются origin, исходная ветка и SHA. PR из fork пока отклоняются. Список ограничен
100 открытыми PR. Fetch не выполняется автоматически; отставшую ветку нужно синхронизировать.

## Остановка и восстановление

«Остановить» завершает принадлежащие запуску процессы и потом сохраняет отмену.
Отдельный guardian следит за liveness pipe: даже при аварийном завершении backend
его процессы и наследуемые группы завершаются. При следующем старте незавершённые
запуски становятся `interrupted`, ожидавшие зависимости — `skipped`.
Один каталог данных нельзя одновременно открыть двумя экземплярами backend.

Ограничения: macOS/Linux, POSIX-группы процессов; Windows не поддерживается.
Блок ограничен 30 минутами, API — 30 шагами, отдельная API-проверка — 2 минутами.
Вывод процессов ограничен; превышение лимита — явная ошибка, логи и diff имеют
отмеченное ограничение размера. Известные секреты и токены редактируются перед
сохранением логов/результатов, но секреты не следует помещать в текст промптов.

## Структура и проверка

```text
backend/
  cmd/service/                 запуск приложения
  internal/
    api/http/                  HTTP и статические ресурсы
    config/app/                параметры запуска и расположение настроек
    service/graph/             DAG, ссылки, подстановка, переименование
    service/run/               планировщик, снимки, отмена, профили
    repository/sqlite/         база и восстановление
    repository/git/            ветки, worktree, коммиты и diff
    repository/settings/       чтение и атомарная запись settings.json
    repository/executorconfig/ чтение прежнего executors.json
    client/github/             PR-контекст GitHub
    client/chatcompletion/     совместимый API и файловые инструменты
    cli/codex/                 Codex CLI
    cli/claude/                Claude Code
    cli/process/               процессы, guardian, редактирование секретов
    model/                     общие контракты без IO
    testutil/                  общие тестовые фикстуры
  migrations/                  SQL и embed
frontend/                      рабочий интерфейс
examples/settings.json         пример пользовательских настроек
```

```sh
make test
make check
make build
```

Тесты используют временные Git-репозитории, реальные локальные подпроцессы и
протокольные фикстуры API/CLI; фикстуры не подключаются в рабочем приложении.
Для отдельной проверки настоящего Codex с установленной авторизацией:

```sh
cd backend
FLOWLINE_LIVE_CODEX=1 go test ./internal/cli/codex -run '^TestLiveCodex$' -v -count=1
```

Эта команда реально вызывает модель. Результаты и недоступные проверки текущей
сессии приведены в `backend/docs/verification.md`.
